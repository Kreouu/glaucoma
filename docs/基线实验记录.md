## workers 速度短测（已完成）

使用 `scripts/benchmark_training.py`，固定 batch=16、256 输入、JPEG 缩小解码、AMP、加权 BCE=3；在同一训练图片顺序上按 4→6→8→8→6→4 测试，每次先预热 20 批，再测 200 批。临时模型不保存，原有实验未修改。结果与说明见 `outputs/speed_workers_001/report.md`。

| workers | 两次合计吞吐（图/秒） | 等待下一批均值（ms） |
|---|---:|---:|
| 4 | 353.7 | 1.08 |
| 6 | 373.0 | 0.23 |
| 8 | 376.9 | 0.23 |

相对 4，6/8 的吞吐均值提升约 5.5%/6.6%；4 的两次结果也有明显波动（333.6 与 376.4），不足以据此认定增加 worker 能带来稳定大幅收益。真实 trial 的可见 batch 等待约占 0.5%–3%，读图 CPU 工作与 GPU 计算重叠，不能将其当作全部解码耗时。

显存驻留的随机输入及另测的固定真实图片 batch 均未明显提速，不能当作严格训练性能上限。CUDA event 阶段也包含主线程提交间隙；当前证据只能支持数据等待并非唯一主要待优化项，尚未通过 profiler 精确区分 kernel、CPU 提交和同步成本。建议先维持 workers=4，把后续速度优化与训练效果对照分开版本管理，不追求单纯提高 GPU 利用率。
